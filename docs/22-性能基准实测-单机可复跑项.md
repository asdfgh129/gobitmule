## 一、结论摘要

2026-11-17 在实验室主机 A 上用 `cmd/udbench`（`ud.bench/v1`）对当前 `udd` 二进制实测
（`2026-11-17T01:12:59Z` 启动，长稳至 `03:13Z` 结束）：

```text
1000 任务常驻内存增量    8.6MB（空载 23.3 → 1000 任务 31.9）   → PASS
启动时间（含 1000 恢复）  261ms（另 1ms 后 /tasks 计数 = 1000）  → PASS
创建→首字节 P99          P50 17.7ms / P99 45ms / max 46.9ms    → PASS
1000 任务长稳（2h）      峰值增量 12.5MB（240 次采样）          → PASS
```

- **四项执行的指标全部达标**（内存、启动、创建时延、2h 长稳）；长稳 2h 内 RSS 未出现
  单向增长趋势（峰值 35.7MB = 末值 35.7MB，见 §四）。
- 证据归档于 [`docs/evidence/bench-2026-11-17/`](evidence/bench-2026-11-17/)：
  `bench.json`、`rss_series.txt`、`SHA256SUMS`。
- **链路吞吐不在本报告**：NFR-PERF-01 的双机结果见 [`20`](20-NFR-PERF-01双机应用层基准实测报告.md)；
  真千兆链路下的原 80MB/s 口径按项目发起人 2026-11-17 指示**略过**（本环境无千兆链路）。

2026-11-18 追加（`cmd/udffmpegbench`，真实 ffmpeg 5.1.2，同一台主机 A）：

```text
ffmpeg exec 开销         中位 163.1ms / P95 187.7ms / max 190.1ms  → PASS
分片哈希 vs 真实转码     并发 89.8MiB/s = 单跑 123.5MiB/s 的 73%    → PASS
```

- 两项判据、方法与边界见 §九；证据归档于
  [`docs/evidence/ffmpeg-bench-2026-11-18/`](evidence/ffmpeg-bench-2026-11-18/)。
- 这两项是**单机 CPU/exec 观测**，与链路吞吐、L4 互操作、移动端指标互不替代。

## 二、被测对象与方法

| 项 | 内容 |
|---|---|
| 被测二进制 | `dist/udd-linux-amd64`（`CGO_ENABLED=0`、`-trimpath`，与发布构建同参数） |
| 驱动方式 | `cmd/udbench`：`exec` 真实 `udd` 子进程 → `GET /api/v1/healthz` 判定就绪 → `POST /api/v1/tasks` 建任务 → `GET /api/v1/tasks/{id}` 读进度 |
| 数据源 | `udbench` 内置 fixture（回环 HTTP）：`/fast/*` 立即返回 64KiB；`/trickle/*` 声明 64MiB 但每 100ms 仅发 1 字节（任务长期处于**真实传输中**，磁盘与带宽开销可忽略） |
| 配置 | `maxConcurrentTasks: 5`（默认值）、`maxConnectionsPerTask: 4`、`chunkSize: 4MiB`；`allowLoopbackForDev: true` 仅用于让真实 SSRF 守卫接受回环 fixture |
| RSS 读数 | Linux `/proc/<pid>/status` 的 `VmRSS`（macOS 走 `ps -o rss=`；平台不可读时该项如实标 `NOT_EXECUTED`） |
| 主机 | 实验室主机 A（隔离段 `192.168.1.222`）：linux/amd64，**1 vCPU**，kernel 6.2.0-39-generic，Ubuntu 23.x（与 `19` / `20` 同一台机器）；单核是**最不利**配置，故本节数字不依赖多核并行 |

2026-11-17 三项的判定口径（与 `12` §5 一一对应；2026-11-18 追加两项见 §九）：

| 指标 | 判据 | 实现要点 |
|---|---|---|
| 1000 任务常驻内存增量 | ≤ 300MB | `RSS(1000 任务) − RSS(空载守护进程)`；1000 个任务同时驻留（5 个在传输、其余在调度队列） |
| 启动时间（含 1000 任务恢复） | ≤ 3s | 进程 `exec` → `/healthz` 200。`app.Run` 在 `net.Listen` **之前**调用 `Recover()`，故该时间天然包含 1000 条任务的 FromDB 恢复；同时断言 `GET /tasks` 总数为 1000 |
| 任务创建→开始传输 P99 | ≤ 1s | 顺序创建 200 个直连任务，每次等到 `bytesDone>0` 后立即取消；轮询粒度 5ms。**不含解析**：输入为直连 HTTP，测的是调度分发链路 |

## 三、复跑方式

```bash
# 任一台 Linux 主机（真实二进制 + 真实 REST + 真实传输）
go build -o udd ./cmd/udd
make bench-perf                      # 默认 BENCH_TASKS=1000 BENCH_SOAK=2h
# 或直接调用：
go run ./cmd/udbench --udd ./udd --tasks 1000 --soak 2h --sample 30s \
  --latency-samples 200 --out dist/bench.json
```

- 立即返回的冒烟运行：`BENCH_TASKS=30 BENCH_SOAK=0 make bench-perf`（该模式**不会**给出长稳结论）。
- 退出码：`0` = 所有执行的指标均 PASS；`1` = 至少一项 FAIL（`NOT_EXECUTED` 不影响退出码）。
- **不接入 CI**：与 `l4-run` / `perf-lab` / `peer-matrix` 同级——完整运行需 2h 长稳，CI 不做。

## 四、实测数据

### 4.1 1000 任务常驻内存

| 采样点 | RSS |
|---|---|
| 空载守护进程（就绪后静置 3s） | **23.3 MB** |
| 1000 任务全部驻留（稳定 5s 后） | **31.9 MB** |
| 增量 | **8.6 MB**（目标 ≤ 300MB） |

> RSS 取 `/proc/<pid>/status` 的 `VmRSS`（kB）换算为 MB 后保留一位小数；增量按**未取整**读数计算，
> 故表内 `31.9 − 23.3 = 8.6` 与逐位相减可能差 0.1。`bench.json` 的 `metrics[].measured` 串用未取整
> 读数格式化，末位偶有 ±0.1MB 差异，`raw` 字段与本表取同一位数。

### 4.2 启动时间（含 1000 任务恢复）

| 里程碑 | 耗时 |
|---|---|
| 进程 `exec` → `/healthz` 200（含 `Recover()`） | **261 ms** |
| `/healthz` 之后 → `GET /tasks` 计数 = 1000 | **+1 ms**（相对 `/healthz`，非累计） |
| 恢复任务数 | **1000**（= 建库任务数，无丢失） |

### 4.3 创建→首字节时延（200 次顺序创建）

| 统计量 | 值 |
|---|---|
| P50 | **17.7 ms** |
| P99 | **45 ms**（目标 ≤ 1000ms） |
| 最大 | 46.9 ms |
| 轮询粒度 | 5 ms |

### 4.4 长稳 2h（采样间隔 30s，共 240 次）

| 统计量 | 值 |
|---|---|
| 峰值 RSS | 35.7 MB |
| 最低 RSS | 31.0 MB |
| 末次 RSS | 35.7 MB |
| 峰值增量（相对空载） | **12.5 MB**（目标 ≤ 300MB） |

判定：**PASS** —— 2h 窗口内峰值增量仍在 300MB 以内，且末值未持续攀升。

- 采样区间 `01:13:14Z` → `03:12:44Z`（240 次 × 30s，恰为 2h；每次采样写入 `rss_series.txt`）。
- 峰值 **35.7MB** 与末值 **35.7MB** 相同：后段一直贴着同一水平线，**无单向爬升**；
  单核主机上 1000 任务（5 个并发槽位、其余排队）的常驻开销始终在 36MB 以内。

## 九、2026-11-18 补测：真实 ffmpeg 的 exec 开销与哈希并发

### 9.1 被测对象与方法

| 项 | 内容 |
|---|---|
| 被测代码 | `internal/postproc` 的 `Transcode`（`ffmpeg-transcode`），走真实 `exec`，输入为**已下载的本地文件**，输出 `<target>.transcode.part` |
| 工具 | `cmd/udffmpegbench`（`ud.ffmpegbench/v1`），`make bench-ffmpeg`；**不接入 CI** |
| ffmpeg | Ubuntu 22.04 的 `ffmpeg 5.1.2-3ubuntu1`（**GPL** 构建，含 libx264/aac），探测通过后才计时；`--enable-nonfree` 构建会被判 `E_CAPABILITY_UNAVAILABLE` |
| 主机 | 实验室主机 A（同 §二）：linux/amd64，**1 vCPU**，3.9GB RAM；单核是**最不利**的并发配置 |
| exec 开销 | 本地生成 2s/320x240 视频，连续 20 次 `Process`（每次真实编码 + 复用输出清理），统计中位/P95/最大 |
| 哈希并发 | 4MiB 分片 SHA-256 先**单跑** 256MiB 取基准；再与一个 10s/640x360 的真实转码**同时**跑，比较哈希吞吐并确认两侧都完成 |

判定：exec 中位 ≤ 500ms；并发时哈希吞吐 ≥ 单跑 25% 且两侧均完成。
阈值刻意宽松——本条要证明的是「都不被饿死」，不是吞吐承诺。

### 9.2 实测数据

| 指标 | 实测 | 目标 | 判定 |
|---|---|---|---|
| ffmpeg exec 开销 | 中位 **163.1ms**、P95 187.7ms、最小 159.8ms、最大 190.1ms | 单次 200–500ms 可接受 | **PASS** |
| 哈希并发吞吐 | 单跑 123.5MiB/s（2173.8ms）→ 并发 89.8MiB/s（2989.1ms），为单跑 **73%**；同期转码 1881.0ms 完成、64 片全部校验 | ≥ 单跑 25%，两侧完成 | **PASS** |

### 9.3 复跑方式

```bash
go build -o /tmp/udffmpegbench ./cmd/udffmpegbench
/tmp/udffmpegbench -ffmpeg /usr/bin/ffmpeg -work /tmp/ffbench -samples 20 -hash-mb 256 \
  -out dist/ffmpeg_bench.json
# 或：make bench-ffmpeg FFMPEG_BIN=/usr/bin/ffmpeg
```

- 退出码：`0` = 已执行项全部 PASS；`1` = 至少一项 FAIL；`NOT_EXECUTED` 不影响退出码。
- 缺 ffmpeg、探测失败或生成测试视频失败时，报告写 `NOT_EXECUTED` 并给出原因，**不会**编造数字。
- **首次真实运行捕获到一个真 bug**：输出名恒为 `<target>.transcode.part`，ffmpeg 无法从扩展名
  推断容器，需显式 `-f mp4|matroska|webm`；已修复并加 `TestTranscodeSelectsExplicitMuxer` 回归用例。
  这正是「真实 ffmpeg 补测 ≠ 单测通过」的价值。

### 9.4 边界

- 只测**单机 exec 与 CPU 并发**：不涉及网络、磁盘吞吐或移动端，也不等同于转码吞吐能力。
- 数字是**该主机、该 ffmpeg 构建**的时点值；换 CPU/构建会变，复跑以本文命令为准。
- 并发判据是「不互饿」，不是「转码不降速」：1 vCPU 上 73% 的哈希吞吐属正常争用结果。
