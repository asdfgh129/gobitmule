# ADR-0027 多文件下载与容器合并（分离 A/V 双流兑现）

- **状态**：Accepted（项目发起人 2026-11-21 全权授权执行 P3 开发；代行五角色，非实名会签，依 `17` §1 P0 先例）
- **日期**：2026-11-21
- **决策者**：项目发起人（用户）指令「继续 P1/P2 未完成的任务，如已完成，请执行 P3」
- **关联**：ADR-0010（双层解析 §决策 4/验证清单）、ADR-0011/0012（后处理契约）、ADR-0023/0024（流传输）、`03` UC-04 / FR-SRC-02 / FR-PST-01、`05` §3 / §4、`06` §3 DDL / §4.4 / §5、`07` v0.14、`12` §3.3、`14` WBS 12/13/14 P3 余项、`docs/README`

## 背景

P2 验收「分离流合成为可双击播放 MP4 且**无 ffmpeg**」在 2026-11-20/21 的
WBS 12/13/14 交付中被显式推迟到 P3（ADR-0010 实现注：「调度器当前每任务只下载
`Resource.Files[0]`，尚无第二条流的分片计划与合并输入」）。`docs/06` §4.4 已给出
分离流的既定资源形态（多 selected Files + post_process remux），`14` WBS 12 行
将「分离 A/V 两条下载 + Remux 合并」列入 P3 计划。Remux（WBS 14）本身已支持
多输入 TS → 视/音轨 → 单 MP4——缺口全在调度器侧。

## 决策

1. **每文件一条源 URL**：`ResourceFile` 新增 `URL` 字段（`files` 表 DDL v2 增列
   `url TEXT NOT NULL DEFAULT ''`）。单文件资源的 URL 仍走 Mirrors，字段留空；
   每个非空 URL 由 Resolver 在持久化前过 SSRF Guard。
2. **迁移运行器升级为记录式**：v1 runner 每次 Open 重跑全部迁移、依赖幂等 SQL，
   无法承载 `ALTER TABLE ADD COLUMN`。v2 runner 以 `schema_migrations` 表记录
   已应用迁移（幂等建表），旧 v1 库首次以 v2 runner 打开时补记全部文件名
   （v1 SQL 本就幂等，跳过重跑安全）。`schema_version` = 迁移文件数（现为 2）。
3. **顺序多文件下载**：调度器每任务按 Index 顺序逐个下载 selected 文件——
   每文件独立 chunk 计划（`chunks.file_idx` 既有列）、独立 `.part` 路径
   （option 键 `temp_path`（文件 0，兼容不变）/ `temp_path:{i}`）、独立校验。
   传输接口零改动：调度器对每文件构造单文件子 Resource（Mirrors = 该文件 URL）
   调同一 Transport.Run，ChunkWriter 以 file_idx 声明分片（`NextForFile`）。
4. **限速权威不变**：一个任务一个 Budget 租约，跨文件复用；分片批量刷盘、
   事件与速度计数均按任务聚合。
5. **崩溃恢复逐文件**：`Recover` 将分片按 file_idx 分组，逐文件校验各自
   `.part` 字节（无该文件 `.part` → 该文件分片全部回 pending），进度按
   全部文件合计；单文件任务行为与 v1 完全一致。
6. **合并提交**：全部文件校验通过后，后处理器（多文件默认 `remux`；用户显式
   选择其它处理器则尊重）收到全部 `.part` 路径，输出经核心原子 rename 提交，
   `Commit(fileIdx=0, final)` 记最终路径；合并输入 `.part` 随后删除。
   校验失败的分片逐片重置回 pending 并暂停重排——沿用单文件语义，绝不
   生成残缺合并文件。
7. **yt-dlp 分离发射**：`ChooseFormats` 的分离 A/V 结果在两路均带声明尺寸
   （`filesize` / `filesize_approx`）时发射双文件资源（尺寸未知仍干净拒绝——
   分片计划需要精确大小）；站点 `http_headers` 以并集随 Resource 下发。
8. **resolver 站点头持久化修正**：resolve 阶段此前把 `res.Headers` 置 nil，
   站点必需头（Referer/UA）在持久化与 `injectHeaders` 两处断流——修正为
   SaveResource 经 `StripSensitiveHeaders`（docs/06 §6 既有机制）剥离敏感项
   后持久化非敏感头；`injectHeaders` 改为合并（resolver 头 < 任务选项头 <
   凭据），替代式覆盖会静默丢弃站点头。

## 发现并修复

- **站点头双断流**（决策 8）：yt-dlp/lux 的 `http_headers` 在「持久化置 nil」
  与「injectHeaders 全量替换」两处丢失——真实 CDN（B站等）依赖这些头，断流
  使任何站点头流量实际不可用。两层修正 + 单元/集成断言。
- **迁移重跑崩溃隐患**：v1 runner 对非幂等迁移会在第二次 Open 失败（
  `duplicate column name`），由 drill 测试实测发现（决策 2）。
- **版本断言盘点**：DDL v2 使 `schema_version=2`，备份/迁移/drill 测试的
  模拟坏升级相应从 `'2'` 升至 `'3'`、恢复基线从 1 升至 2。
- **可达漏洞修复**：govulncheck 抓到 lux HTML 解析路径引入的
  `golang.org/x/net@v0.60.0` GO-2026-6860（`ixigua.init → html.Parse` 可达），
  升级至 `v0.62.0` 后 vuln 门禁 PASS（`no known vulnerabilities`；1 个不可达
  require 级漏洞按 `11` §3 口径如实披露）。

## 验证（ADR-0010 验证清单兑现）

- **调度器级集成**（`TestMultiFileSeparatedStreamsRemuxToMP4`，真实 HTTP 传输 +
  真实 Remux，零 ffmpeg）：两条分离 TS 流（H.264 视频流 / AAC 音频流）各自成
  chunk 计划与 `.part`，顺序下载、逐文件校验、remux 合并为单 MP4，样例字节
  双轨齐备，`.part` 合并后清理，任务 Completed。
- yt-dlp 分离格式（带尺寸）→ 双文件资源单测；无尺寸 → `E_CAPABILITY_UNAVAILABLE`
  维持诚实拒绝。
- 单文件路径回归：store drill / 崩溃恢复 / 备份回滚 / 全量 22 包与迁移 v2 兼容。

**仍不宣称**：真实 YouTube 站点端到端（CI 禁直连，回放 fixture 待建）；
Deno/EJS；HLS 多 rendition / DASH 多 AdaptationSet 的分离发射（其调度侧已具备，
属后续包）；合并吞吐与超大文件上限沿用 Remux 的 1GiB 输入帽。

## 后果

- P2 验收「无 ffmpeg 不退化 720p」的技术路径打通：yt-dlp 高画质分离流 +
  自有合并不再拒绝；「删除 ffmpeg 后 1080p 合并」调度器级集成测试在 CI 可跑。
- `files` DDL v2 进入备份/恢复/migrate 面：备份包 schema v2、恢复校验按
  `CurrentSchemaVersion()` 自动适配；旧 v1 备份恢复后由迁移补列。
- 解析链与传输注册表零变化；WBS 12/13/14 的「P3 余项」仅剩真实站点回放与
  Deno/EJS。
