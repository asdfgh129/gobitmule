> **本报告记录一次真实双机应用层基准**，不是评审签署表。结论只在
> **ADR-0022 修订后的口径**下成立：门槛为「≥ 可用链路理论上限 × 80%」，
> 当前百兆隔离段取 **≥ 10MB/s**。原「千兆内网 1GiB ≥ 80MB/s」是历史时点值，
> 在本百兆链路上**不适用、也未宣称达到**；链路升级至真千顿时自动恢复原口径。

## 一、结论摘要

2026-11-16T13:16:02Z，主机 B 用真实 HTTP Range 服务端提供 1GiB 确定性数据，
主机 A 用项目真实 `internal/transport/http` Range Transport 下载并逐片校验：

```text
1 GiB (1073741824 bytes) in 91.367 s = 11.21 MB/s
chunks verified: 4096 / 4096
bytes verified: 1073741824 / 1073741824
nfr_perf_01.met = true   (threshold >= 10.00 MB/s, ADR-0022)
```

- 应用层吞吐 **11.21 MB/s**，同链路 iperf3 实测 **94.15Mbps ≈ 11.22 MB/s**
  （单流与 8 流一致），应用层达到链路容量的 **约 99.9%**。
- ADR-0022 的 80% 门槛在当前链路约为 **8.98 MB/s**；本次采用更保守的
  **10 MB/s**（约为链路的 89%）仍达标，因此结论不依赖「刚好压线」。
- 证据归档于 [`docs/evidence/nfr-perf-01-2026-11-16/`](evidence/nfr-perf-01-2026-11-16/)：
  `nfr_perf_01.json`、`iperf3-P1.json`、`iperf3-P8.json`、`link.json`、
  `SHA256SUMS`。

## 三、可复跑命令

1. **构建与部署**（控制面）：

   ```bash
   GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o udperf ./cmd/udperf
   scp udperf root@192.168.34.222:/root/l4lab/bin/udperf
   scp -P 54022 udperf root@112.5.60.4:/root/l4lab/bin/udperf
   ```

2. **主机 B 起服务端**：

   ```bash
   /root/l4lab/bin/udperf --serve \
     --listen 192.168.1.221:18080 --bytes 1073741824
   ```

   首行输出 `{"schema":"ud.perf-serve/v1","url":"http://192.168.1.221:18080/perf.bin",...}`。

3. **主机 A 跑应用层基准**：

   ```bash
   /root/l4lab/bin/udperf \
     --url http://192.168.1.221:18080/perf.bin \
     --bytes 1073741824 --connections 4 \
     --min-mb-s 10 --require-met \
     --out /root/l4lab/evidence/nfr_perf_01_dualhost.json
   ```

   控制面也可用 `make perf-lab PERF_LAB_URL=http://192.168.1.221:18080/perf.bin`。

4. **链路对照（iperf3）**：

   ```bash
   # 主机 B
   iperf3 -s
   # 主机 A
   iperf3 -c 192.168.1.221 -t 10 -P 1 --json
   iperf3 -c 192.168.1.221 -t 10 -P 8 --json
   ```

## 四、实测数据

### 4.1 应用层（`ud.perf/v1`）

| 指标 | 值 |
|---|---|
| 工作量 | 1GiB（`1073741824` 字节），4 连接，256KiB 分片 |
| 传输路径 | `internal/transport/http` 真实 Range 路径 |
| 服务端 | 主机 B `udperf --serve`，64KiB 确定性重复模式 |
| 耗时 | `91.367s`（`elapsed_ms=91367`） |
| 吞吐 | **11.207 MB/s** |
| 字节校验 | `1073741824 / 1073741824` |
| 分片校验 | `4096 / 4096` |
| 门槛 | `≥ 10.00 MB/s`（ADR-0022，百兆段） |
| 判定 | **`nfr_perf_01.met=true`** |

### 4.2 链路容量（iperf3 3.12）

| 流数 | 发送 | 接收 | 接收 MB/s | 重传 |
|---|---|---|---|---|
| 1 | 94.49Mbps | **94.15Mbps** | **11.224** | 75 |
| 8 | 95.27Mbps | **94.14Mbps** | **11.223** | 2418 |

单流与 8 流接收速率一致，说明瓶颈是链路物理限速（约 100Mbps），
不是 TCP 窗口或并发不足。

### 4.3 口径换算

**单位说明**：本项目 `udperf` 沿用既有记法，`MB/s = 1024 × 1024 字节/秒`
（即 MiB/s），`1GiB / 91.367s` 与 `iperf3` 的换算都按此口径。按十进制 MB
（10⁶ 字节）表示时，94.15Mbps 约为 **11.77MB/s**；ADR-0022 中的
「94.1Mbps ≈ 11.8MB/s」即十进制表述，与本报告的 11.22MB/s 不矛盾。

- 链路容量取 iperf3 接收值 **11.223 MB/s**（1024² 记法）。
- ADR-0022 的 80%：`11.223 × 0.8 = 8.978 MB/s`。
- 本次采用门槛 **10 MB/s**（约为链路容量的 89.1%），比 80% 更严格。
- 应用层 **11.207 MB/s ÷ 11.223 MB/s ≈ 99.9%**，高于门槛 12.1%。

## 六、边界与不宣称事项

1. **不是千兆达标**：链路实测 94.15Mbps，结论只在 ADR-0022 的百兆段门槛下成立；
   **不宣称**「千兆内网 ≥ 80MB/s」已达成。链路升级至真千兆后，必须按原
   80MB/s 口径重跑，ADR-0022 的修订自动失效。
2. **不是公网条件**：两机在隔离段直连，没有 ISP、跨路由、丢包抖动等公网因素；
   不宣称公网下载速度。
3. **单次实测**：本报告是一次可复跑的确定性测量，不是长期稳定性/长稳压测；
   1000 任务常驻内存、并发信号量等其余 §5 指标不在本报告范围。
4. **不替代 L4**：`BT-01..BT-14` 是互操作判据，本报告是 HTTP Range 吞吐判据；
   `docs/19` 的 14/14 不能替代本报告，反之亦然。
5. **回环参考仍为 `met=false`**：`make perf` 的 `dist/perf.json` 继续固定
   `nfr_perf_01.met=false`；只有本报告的双机模式可以置 `true`。
6. **`udperf` 的 lab guard**：双机模式为访问隔离段私网地址，显式关闭
   `BlockPrivateNetworks` 且只允许目标端口、禁重定向；该放宽只存在于
   `cmd/udperf` 实验室命令，不影响产品默认 SSRF 策略。
